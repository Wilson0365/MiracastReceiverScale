# Independent exit review

Review of the uncommitted changes against aefabf0. No production files edited. The Android API 24 key-set issue has already been fixed and is excluded below.

## Important findings

1. **P1: DLNA/Cast can start fresh playback after the exit STOP broadcast.** `CastReceiverService.kt:419-426` stops AirPlay, awaits Miracast, and only then stops the other receivers. During P2P callback timeouts this leaves UPnP and Cast open for seconds. `dlnaRenderer.onSetUri` at line 277 has no stopping check and starts PlayerActivity directly. A sender sending SetAVTransportURI during teardown can therefore create a player after the only global ACTION_STOP; closing UPnP later does not stop that new ExoPlayer. CastPlayerBridge also remains open and can dispatch queued loads until its late stop. This violates the central TV Back contract. **Smallest fix:** close admission to DLNA/Cast immediately when beginExit starts, add stopping guards to DLNA callbacks (particularly onSetUri), close/disable CastPlayerBridge immediately on the main thread, and send a final playback STOP after shutting receiver admission. Keep network teardown on IO, but CastPlayerBridge is explicitly a main-thread adapter and its stop currently runs on IO while its ArrayDeque/token/closed fields are accessed on main.

2. **P1: Exit before network initialization skips owned Miracast residue entirely.** `CastReceiverService.kt:424` returns true when initialized is false. A previous process can have left sessionOpen, root/framework IE, P2P group or wifi_display_on=1; the current service can be waiting for network and hence have no receiver objects. Back persists SYSTEM and stops the foreground service without auditing/cleaning these resources, leaving the system receiver blocked indefinitely until another app launch. The dirty marker survives, but the required cleanup was never attempted. **Smallest fix:** provide a teardown-only Miracast controller/cleanup path when initialization has not occurred, and await its residue cleanup without starting advertisements or playback services.

3. **P1: A queued legacy AirPlay RECORD start can resurrect media after sender disconnect.** `AirPlayReceiver.kt:290-293` queues pipeline setup and only checks the receiver-wide stopping flag. `onStreamingStopped` and disconnectSender release components synchronously but leave stopping false to keep the receiver available. If the sender sends RECORD and immediately closes or TEARDOWNs before the queued coroutine acquires the receiver monitor, cleanup happens first, then the old queued task creates AudioPlayer/VideoDecoder and emits CONNECTED. Serialization does not make this task belong to the live session. **Smallest fix:** increment a session generation on full session end/local disconnect, capture the generation when scheduling onStreamingStarted, and reject the task under the same monitor when its generation is stale. Keep the global stopping check for full service stop. Add a regression test for end-before-queued-start.

4. **P2: A quick manual reopen is dropped when exiting an uninitialized service.** `CastReceiverService.kt:398` records restartRequested, but `onDestroy` at lines 552-555 returns before the restart block at line 568 when initialized is false. A manual start delivered while the exit coroutine is suspended saving SYSTEM is therefore acknowledged and silently discarded. **Smallest fix:** make scope cancellation and the restart block common to both initialized and uninitialized destruction paths.

5. **P2: Awaited Miracast cleanup does not await its audio thread.** `RtpReceiver.kt:222-225` joins only its coroutine scope. `MiracastAudioPlayer.release` at lines 93-98 merely interrupts its independent Java Thread and drops the reference; AudioTrack and codec release happen later in that thread's finally at lines 132-134. The thread may still be in WRITE_BLOCKING at line 325, which Java interruption does not guarantee to unblock. Thus WfdServer.stopAndAwait can return true and sessionOpen can be cleared while audio and codec resources remain live. **Smallest fix:** retain the stopping audio thread, ensure its AudioTrack write is unblocked, await thread termination with a bounded wait, and include that result in RtpReceiver.awaitStopped so a timeout retains the dirty flag.

## Additional lifecycle concern

`MiracastController.enterApp` checks stopping only on entry (line 256). An enterApp already suspended inside P2P setup retains the process mutex when shutdownAndAwait sets stopping and waits for it. It can still finish discovery and wfd.start before shutdown gets the lock, allowing connection/player startup during exit. Cancel the controller's ongoing convergence work at shutdown start, or check stopping after suspending setup steps and roll back before starting WFD. A queued reconcile is guarded correctly, but an in-progress converge is not. This can be handled with finding 1's immediate admission shutdown and a controller cancellation guard.

No new tests were run by this read-only reviewer; author was running the full suite. These findings are concrete control-flow/resource-ownership issues, rather than formatting polish.

## Resolution
All findings above are addressed before release: playback callbacks dispatch through main-thread admission; Cast bridge closes at exit start; a standalone Miracast controller cleans residue without network initialization; AirPlay generation tokens reject stale setup; uninitialized destruction preserves explicit manual restart; audio shutdown stops AudioTrack writes and joins the worker; controller convergence is canceled before acquiring the shutdown mutex.

User steering after review: DLNA sender stop stays ready; Miracast and AirPlay screen-mirror sender stop exit all receivers. URL-video handoff remains uninterrupted.

Verification: 65 JVM tests passed; debug/release compilation and assembleRelease (including lintVitalRelease) passed. Full lintRelease reports existing issues and is not claimed green. No Android device was attached for a hardware cast test.
